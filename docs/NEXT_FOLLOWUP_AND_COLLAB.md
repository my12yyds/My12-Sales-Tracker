# 下次跟进提醒、协作销售、批量录入与看板增强（v2）

本轮在原有「线索工作台」基础上补齐了 5 组能力。所有权限校验仍在云函数中完成，前端隐藏只影响体验；没有修改历史数据，也没有自动迁移字段。

## 一、下次跟进提醒

| 项 | 说明 |
| --- | --- |
| 写入 | 跟进页新增「下次跟进日期（可选）」，保存到 `followUps.nextFollowUpDate`，同时汇总到 `leads.nextFollowUpAt`（中国日历日零点） |
| 摘要规则 | 只有本次跟进不早于 `lastFollowUpAt` 时才更新线索摘要；补录历史记录只增加跟进条数，不回退状态和最近跟进时间 |
| 自动清除 | 状态变为成交/流失，或本次跟进未填下次日期时，`nextFollowUpAt` 字段被删除（不做显式 null，避免空值在范围比较中被当作最小值） |
| 列表筛选 | 状态筛选旁新增下拉：全部待跟进 / 今日待跟进 / 已逾期 / 未来7天。范围查询使用中国时区自然日，成交与流失的线索自动排除 |
| 列表展示 | 卡片右侧显示「逾期 N 天 / 今日待跟进 / 明日待跟进 / MM-DD 待跟进」，逾期为红、今日为橙 |
| 待办入口 | 主播与销售首页新增待办卡片（今日 / 逾期 / 未来7天），点击直接带筛选进入列表；该入口筛选不写入本机偏好 |
| 统计 | `userStats` 增加 `dueToday`、`overdue`、`dueWeek`，用 `count()` 计算，不受分页影响 |
| 导出 | CSV 新增「下次跟进」「是否逾期」两列 |

日期规则：跟进日期不能晚于今天（中国时区），下次跟进日期不能早于本次跟进日期；两者都必须是真实日历日。

## 二、协作销售管理

`leadAssignSales` 云函数原本已实现，但前端从未调用，等于一条走不通的能力。本轮补齐：

- 新增 `groupMembers` 云函数，列出本组销售（只返回 `_id` 与姓名，不下发手机号/微信号）
- 线索详情页新增「协作销售」区块，主播可「添加销售」（底部选择器）或点 chip 上的 ✕ 移除
- 至少保留一名协作销售；移除不会删除该销售的历史跟进记录
- 管理员查看全量数据但按设计不参与写操作，因此看不到该区块

## 三、批量录入与组内查重

- 新增 `leadCreateBatch` 云函数：接收字符串或数组，1~100 条；按换行、逗号、分号、顿号切分，自动去掉空格/连字符/括号，识别全角数字
- 组内查重：一次 `in` 查询取出本组已存在的号码，重复的直接跳过并在结果里列出，不会产生重复线索
- 分配策略：指定销售则全部写入该组合；未指定则按「当前最轻负载」逐个分配，批量内部也会递增计数，避免全部堆给同一个销售
- 每条线索写入 `batchId`，便于后续按批次核查或回滚
- 主播录入页新增「单条 / 批量」切换，输入时实时显示可录入、本次重复、无法识别的数量
- 单条录入遇到本组重复号码时，云函数返回 `duplicate: true`，前端弹窗提示后可选择「仍然录入」（`force: true`），不会静默覆盖

## 四、看板增强与统计修复

| 变化 | 说明 |
| --- | --- |
| 修复截断 | 原实现直接 `db.collection('leads').get()` 读全量，云函数单次查询上限（1000 条）之后的记录会被丢弃，统计偏小；现改为按 `_id` 排序分页读取，单类数据上限 2 万条 |
| 成交转化率 | 成交数 / 线索总数，总体与各组分别统计 |
| 逾期未跟进 | 按 `nextFollowUpAt` 与今日比较，且排除成交/流失 |
| 平均跟进次数 | 总跟进次数 / 线索数 |
| 销售业绩排行 | 每位销售：分配量、已跟进量、跟进次数、成交数、逾期数、转化率；按成交数排序，取前 50 |
| 近似值提示 | 数据量超过 2 万条时返回 `partial: true`，前端显示「指标为近似值」 |
| 跟进记录条数 | 只取 `leadId`/`salesId`/`status` 三个字段，减少传输量 |

## 五、一致性修复

1. `leadDelete` 删除跟进记录改为每批 100 条循环删除。原实现一次 `get()` 后逐条 `remove()`，超过查询上限的跟进记录会变成孤儿数据。
2. `followUpCreate` 的 `durationFromLast` 取 `max(0, 间隔)`，补录历史记录不再出现负数天数。
3. 摘要字段只在「本次跟进为最新一条」时更新，避免补录旧记录把线索状态改回过去。
4. 跟进日期不再接受未来日期，防止 `lastFollowUpAt` 被推到未来导致提醒失效。

## 六、部署步骤

1. 本地执行 `npm test`（65 项，含新增的待跟进筛选、日期校验、号码解析、查重与跟进摘要用例）和 `npm run check:public`。
2. 上传并部署以下云函数（首次需云端安装依赖）：
   - 修改：`leadList`、`leadCreate`、`followUpCreate`、`followUpList`、`leadDelete`、`adminDashboard`、`userStats`
   - 新增：`leadCreateBatch`、`groupMembers`
   - 未改动但被前端调用：`leadAssignSales`（确认已部署）
3. 更新小程序端代码（app.wxss、utils、页面）。
4. 云数据库控制台按提示创建索引：
   - `leads`：`groupId + nextFollowUpAt + lastStatus`、`groupId + phone`
   - `leads`：原有排序/日期筛选所需索引保持不变
5. 无需新建集合；`followUps.nextFollowUpDate`、`leads.nextFollowUpAt` 按需写入，历史数据不受影响。

## 七、验收清单

1. 主播录入一条线索，销售跟进并填写「下次跟进日期 = 今天」，返回首页确认「今日待跟进」+1，进入列表能看到橙色「今日待跟进」标签。
2. 把该线索的下次跟进日改成昨天（重新跟进时填写），确认首页「已逾期」+1，列表筛选「已逾期」能查到，且标签为红色。
3. 用成交状态再跟进一次，确认 `nextFollowUpAt` 被清除、该线索不再出现在待跟进筛选中。
4. 补录一条更早的跟进记录，确认线索的「最近跟进」「当前状态」不变，跟进条数 +1。
5. 主播在详情页添加/移除协作销售，确认列表里「协作销售」同步变化；尝试移除最后一名销售应被拒绝。
6. 批量粘贴 5 个号码（其中 1 个已存在、1 个是乱码），确认结果为「成功 3 / 跳过重复 1 / 无效 1」，列表新增 3 条且分摊到不同销售。
7. 单条录入已存在的号码，确认弹窗提示后可选择仍然录入。
8. 管理员看板确认转化率、逾期数、业绩排行与手工计数一致；数据量较大时出现近似值提示。
9. 删除一条有 100 条以上跟进记录的线索，确认 `followUps` 中没有残留该 `leadId` 的记录。

## 八、已知限制

- 本轮未在真实微信环境部署，`npm test` 使用模拟 SDK，不能替代真机与云端验收。
- 待跟进统计依赖 `leads.nextFollowUpAt` 摘要字段；历史线索没有该字段，需要业务侧重新跟进一次才会进入提醒体系，本轮不做数据回填。
- 逾期判断以中国时区自然日为单位，不区分具体时刻。
- 批量录入串行写入，100 条在云函数默认超时内通常可行；若环境较慢建议分批 30~50 条。
- 看板统计在内存中聚合，数据量超过 2 万条后为近似值，需要精确统计应改为聚合查询或数据仓库方案。
- `groupMembers` 只返回本组销售，跨组协作仍不支持（团队之间仍按 groupId 完全隔离）。
