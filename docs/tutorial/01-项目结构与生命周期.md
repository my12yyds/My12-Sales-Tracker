# 01 项目结构与生命周期

> 本章涉及的 API：`App()`、`Page()`、`onLoad`、`onShow`、`onReady`、`onUnload`、`onPullDownRefresh`、`onReachBottom`、`wx.stopPullDownRefresh`

## 1.1 目录约定

微信小程序对目录有硬性约定，不是随便放：

```
My12-Sales-Tracker/
├── miniprogram/              ← 小程序前端（app.json 所在目录）
│   ├── app.js                ← App() 实例，全局只允许一个
│   ├── app.json              ← 全局配置：pages 列表、窗口样式
│   ├── app.wxss              ← 全局样式
│   ├── pages/                ← 页面，每个页面一个文件夹
│   │   └── lead-detail/
│   │       ├── index.js      ← Page() 逻辑
│   │       ├── index.wxml    ← 结构
│   │       ├── index.wxss    ← 样式
│   │       └── index.json    ← 页面级配置（可省略）
│   ├── templates/            ← WXML 模板片段（用 include 引入）
│   ├── utils/                ← 纯 JS 工具，不含 UI
│   └── styles/               ← 共享 wxss
├── cloudfunctions/           ← 每个子目录是一个独立云函数
│   └── leadList/
│       ├── index.js
│       └── package.json      ← 云函数自己的依赖
└── tests/                    ← Node 原生测试，不在小程序包里
```

两个容易混淆的点：

**`utils/` 和 `pages/` 的区别**：`utils/` 里是纯 JS，可以被任何页面 `require`，但不能写 WXML。本项目的 `utils/lead-page.js` 就是个典型——它导出一个函数，返回一份「页面配置对象」，被两个页面共用（见 1.4）。

**`cloudfunctions/` 每个目录都是独立的**。它们**不能互相 `require`**，因为部署时是分别打包上传的。这就是为什么本项目里 `groupId` 的校验逻辑在每个云函数里都重复写了一遍，而不是抽成公共模块。想共享代码只能靠 npm 包或复制粘贴。

## 1.2 app.json：页面注册与启动页

```json
{
  "pages": [
    "pages/login/index",
    "pages/register/index",
    "pages/home/index"
  ],
  "window": {
    "navigationBarTitleText": "通用客户与事项跟进",
    "enablePullDownRefresh": true
  }
}
```

两条规则：

1. **`pages` 数组第一项就是启动页**。本项目是 `pages/login/index`，所以打开小程序先看登录页，登录成功后再 `reLaunch` 到首页。
2. **页面必须在这里注册才能跳转**，没注册的路径 `wx.navigateTo` 会直接失败。

`window` 里的 `enablePullDownRefresh: true` 是全局开启下拉刷新。这个开关**不开的话 `onPullDownRefresh` 永远不会触发**，是最常见的「代码没错但没反应」原因。

## 1.3 App() 与 onLaunch

`miniprogram/app.js` 全文只有十几行，但承担了全局初始化：

```js
App({
  onLaunch() {
    if (!wx.cloud) {
      console.error("请使用 2.2.3 或以上的基础库以使用云能力");
      return;
    }
    wx.cloud.init({
      env: "YOUR_CLOUD_ENV_ID",
      traceUser: true
    });
  },
  globalData: {
    user: null
  }
});
```

三个要点：

- `onLaunch` **全局只执行一次**，小程序从冷启动到退出期间不会重复触发。所以适合放云能力初始化这种「必须最先执行」的动作。
- `wx.cloud` 的存在性检查不是多余的。基础库低于 2.2.3 时这个对象不存在，直接调用会报错，先判断再初始化能给出可读的提示。
- `globalData` 是**内存中的全局变量**，小程序被系统回收后就没了。它不能当持久化存储用，所以本项目 `utils/auth.js` 里还叠了一层 `wx.getStorageSync` 缓存（见[第 07 章](07-本地存储与登录缓存.md)）。

`App()` 里还能拿到 `this`，即应用实例。页面里用 `getApp()` 取：

```js
// miniprogram/utils/auth.js:10
const app = getApp();
if (app.globalData.user && !forceRefresh) {
  return app.globalData.user;
}
```

## 1.4 Page() 与生命周期

每个页面调用一次 `Page()`，传入一个配置对象。本项目最特别的地方是：**这个对象是函数生成的**。

```js
// miniprogram/pages/anchor/leads/index.js 全文
const createLeadPage = require('../../../utils/lead-page');
Page(createLeadPage(true));
```

`sales/leads/index.js` 也几乎一样，只是参数是 `false`。`createLeadPage(isAnchor)` 返回一整套 `data` + 方法，用参数区分「负责人视角」和「成员视角」。

这种写法叫**工厂函数复用**，好处是两个页面的筛选、分页、导出逻辑只有一份代码；代价是读页面时得跳进 `utils/lead-page.js` 才能看到全部逻辑。小程序的 `Page()` 没有官方 mixin 机制，这是最轻量的替代方案。

### 生命周期顺序

打开一个页面：

```
onLoad(options)  →  onShow()  →  onReady()
```

- `onLoad` **只触发一次**，参数是路由 query（见[第 06 章](06-页面路由与参数传递.md)）。适合做「只该做一次」的事，比如读 query 参数。
- `onShow` **每次页面出现在前台都触发**，包括从其他页面返回、从后台切回来。适合放「数据可能已变，要刷新」的逻辑。
- `onReady` 在首次渲染完成后触发，适合操作 DOM 节点（本项目没用）。

离开页面：`onUnload` 只在页面被销毁（`navigateBack` 出栈、`redirectTo`、`reLaunch`）时触发；`onHide` 是页面被遮住但还在栈里（跳到下一页、切后台）。

本项目把这三者的分工用得很清楚：

```js
// miniprogram/utils/lead-page.js:20-27
onLoad(options) {
  // 从首页待办卡片进入时，直接带上待跟进筛选
  const due = options && options.due;
  if (due && DUE_OPTIONS.some(option => option.value === due)) this._initialDue = due;
},
onShow() { this.loadLeads(); },
onUnload() { this._requestId = (this._requestId || 0) + 1; },
```

- `onLoad` 只把 query 里的 `due` 存到实例变量 `this._initialDue`，不直接加载数据；
- `onShow` 负责加载——这样从详情页返回时会自动刷新，看到最新的跟进状态；
- `onUnload` 把请求序号 +1，让还没返回的请求作废（防竞态，详见[第 12 章](12-踩坑清单与调试.md)）。

### 一个真实陷阱：onShow 重复请求

因为 `onShow` 每次返回都会触发，如果用户连续快速进出页面，会同时存在多个在途请求。如果先发的请求后返回，就会用旧数据覆盖新数据。本项目用「请求序号」解决：

```js
// miniprogram/utils/lead-page.js:35-38
const requestId = (this._requestId || 0) + 1;
this._requestId = requestId;
this.setData({ loading: true, error: '' });
try {
  const user = await login({ forceRefresh: true });
  if (this._requestId !== requestId) return;   // 期间又发起了新请求，本次结果丢弃
```

`this._requestId` 挂在页面实例上（下划线开头只是约定，不是私有语法）。这是小程序里处理竞态最省事的做法，比 AbortController 简单，因为 `wx.cloud.callFunction` 本身不支持取消。

## 1.5 setData：唯一能改视图的方式

这是新手最容易误解的地方：

```js
// ❌ 错：数据变了，界面不动
this.data.keyword = 'abc';

// ✅ 对：通过 setData 通知视图层
this.setData({ keyword: 'abc' });
```

`this.data` 是**逻辑层的普通对象**，改它不会触发渲染。`setData` 做的事是：把差异序列化后通过 JSBridge 传给视图层，视图层再更新。所以：

**规则一：只能传可 JSON 序列化的值。** 函数、`undefined`、`Symbol` 传不过去。本项目里所有 `setData` 的参数都是普通对象、数组、字符串、数字、布尔。

**规则二：只传要变的字段，不要整个对象覆盖。**

```js
// miniprogram/utils/lead-page.js:111
this.setData({ rememberFilters: e.detail.value });
```

**规则三：想改嵌套字段，用路径字符串。**

```js
// miniprogram/pages/admin/users/index.js:105
this.setData({ "editDraft.groupId": e.detail.value });
```

`"editDraft.groupId"` 这种带点的字符串是 setData 的语法糖，等价于只替换 `editDraft` 里的 `groupId`，不会重建整个 `editDraft`。

**规则四：setData 是异步的。** 要读渲染后的值，用回调：

```js
this.setData({ loading: false }, () => {
  // 这里可以安全地读渲染结果
});
```

本项目大量在 `await` 之后 `setData`，靠 `await` 的时序天然避开了这个问题，但严格来说 `setData` 完成 ≠ 视图已渲染。

## 1.6 下拉刷新与触底加载

这两个都是**生命周期函数**，但需要配置才能触发。

### 下拉刷新

页面 json 里开启（全局 `app.json` 已开，页面级可以覆盖）：

```json
// miniprogram/pages/anchor/leads/index.json
{
  "usingComponents": {},
  "enablePullDownRefresh": true,
  "backgroundTextStyle": "dark"
}
```

处理函数：

```js
// miniprogram/utils/lead-page.js:25-27
async onPullDownRefresh() {
  try { await this.loadLeads(); } finally { wx.stopPullDownRefresh(); }
},
```

**关键点：必须调用 `wx.stopPullDownRefresh()` 收起加载圈。** 忘了调用，那个转圈会一直挂在那，用户以为卡死了。

这里用 `try/finally` 而不是 `try/catch`，是因为无论 `loadLeads` 成功还是抛错，都必须收起下拉框。`loadLeads` 内部自己吞掉了错误（写进 `data.error` 显示给用户），所以外层不需要再处理。

### 触底加载

```js
// miniprogram/utils/lead-page.js:28
onReachBottom() { if (this.data.hasMore && !this.data.loading) this.loadLeads(true); },
```

触发条件是**页面滚动到底部附近**（默认距底 50px，可用页面 json 的 `onReachBottomDistance` 调整）。

两个判断缺一不可：

- `this.data.hasMore`：没更多数据了就别再请求；
- `!this.data.loading`：上一次还没回来就别叠加请求。

漏掉任一个的典型症状是：滑到底部连续触发 5 次请求，接口被打爆，列表里出现重复数据。

`loadLeads(true)` 的 `true` 表示「追加」而不是「替换」，具体分页逻辑在[第 04 章](04-查询指令与分页上限.md)。

## 1.7 练习

1. **加一个页面**：在 `pages/` 下新建 `about/`，注册到 `app.json`，从 `home` 页加个按钮跳过去。体会「不注册就跳不过去」。
2. **观察生命周期**：在 `lead-page.js` 的 `onLoad`/`onShow`/`onHide`/`onUnload` 里各加一句 `console.log`，然后在真机或模拟器里来回跳转，看打印顺序。重点观察「从详情页返回」时哪些触发了。
3. **故意破坏 setData**：把某个 `this.setData({ keyword: ... })` 改成 `this.data.keyword = ...`，观察输入框还灵不灵。改回来。
4. **验证下拉刷新的坑**：把 `finally` 里的 `wx.stopPullDownRefresh()` 注释掉，下拉一次看效果。改回来。
