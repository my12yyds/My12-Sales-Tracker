# 02 云开发接入与调用云函数

> 本章涉及的 API：`wx.cloud.init`、`wx.cloud.callFunction`、`wx.cloud.database`、`cloud.init`、`cloud.getWXContext`

云开发把「服务端」折叠进了小程序项目里。你不需要买服务器、配域名、申请 HTTPS 证书，只要写一个云函数目录，上传，前端就能调。

这一章讲清三件事：云能力怎么初始化、一次调用的完整请求/响应长什么样、云函数怎么知道「是谁在调我」。

## 2.1 初始化：wx.cloud.init

```js
// miniprogram/app.js:8
wx.cloud.init({
  env: "YOUR_CLOUD_ENV_ID",
  traceUser: true
});
```

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `env` | string | 云环境 ID。在开发者工具「云开发」控制台能看到，形如 `xxx-1a2b3c4d`。传 `"YOUR_CLOUD_ENV_ID"` 会直接报错，必须先换成真实值 |
| `traceUser` | boolean | 是否在云开发控制台的「用户访问记录」里留下访问日志。教学和调试建议开，方便看到谁什么时候调用了哪个函数 |

两个容易踩的点：

**必须在 `onLaunch` 里初始化，且只初始化一次。** 如果放在页面里初始化，冷启动时可能某些页面先于初始化执行，出现「云能力未初始化」的错误。

**初始化不是异步的，但云函数首次调用是。** 冷启动（云函数实例不存在）时第一次调用可能耗时 1~3 秒，之后复用实例会快很多。本项目所有云函数调用都包在 `async/await` 里，用户看到的是 loading 状态，不会感知到冷启动。

## 2.2 一次调用的完整形状

前端发起：

```js
// miniprogram/utils/auth.js:24
const res = await wx.cloud.callFunction({ name: "authLogin", data: {} });
```

云函数接收：

```js
// cloudfunctions/authLogin/index.js:18
exports.main = async () => { ... }
```

`exports.main` 就是入口。**云函数必须导出 `main`**，参数是 `(event, context)`：

- `event`：前端 `data` 传过来的对象，原样反序列化；
- `context`：运行上下文，包含 `appid`、`env` 等信息，本项目没用到。

返回值就是前端拿到的 `res.result`。完整响应结构：

```js
{
  result: { success: true, data: { ... } },   // 你 return 的东西
  errMsg: "cloud.callFunction:ok",
  requestID: "a1b2c3..."                       // 排查问题时报给客服/日志用
}
```

**所以前端永远要多剥一层 `.result`。** 这是新手第一个必然踩的坑：

```js
// ❌ 错：拿不到 success
if (res.success) { ... }

// ✅ 对
if (res.result && res.result.success) { ... }
```

本项目的处理方式（`utils/lead-page.js:75-76`）：

```js
if (!res.result || !res.result.success) throw new Error(res.result && res.result.message || '加载失败');
```

先判空再判 `success`，最后兜底一个默认文案。三层判断看着啰嗦，但少了任何一层，用户看到的可能就是 `undefined` 或者一屏红色堆栈。

## 2.3 统一返回约定

本项目的 16 个云函数全部遵守同一个契约：

```js
// 成功
{ success: true, data: { ... } }

// 失败
{ success: false, message: "给用户看的中文原因" }

// 特殊情况：需要额外标记
{ success: true, needRegister: true, data: { openid } }
```

为什么要统一？因为前端可以写一份通用错误处理：

```js
// miniprogram/utils/lead-page.js:76
if (!res.result || !res.result.success) throw new Error(res.result && res.result.message || '加载失败');
```

不管调的是 `leadList` 还是 `leadDelete`，这句都能用。如果每个云函数返回结构都不一样（有的返 `{code: 0}`，有的返 `{err: ''}`），前端就得为每个接口写一套判断。

**为什么不用抛异常代替 `success: false`？** 云函数抛出的异常传到前端会变成一个笼统的 `errMsg`，`message` 里还带着云开发的内部前缀，不适合直接展示给用户。所以本项目采取「业务错误返回 `success: false`，只有真正的意外才抛异常被 `catch` 兜住」：

```js
// cloudfunctions/leadCreate/index.js:151-154
} catch (error) {
  console.error('创建线索失败:', error);
  return { success: false, message: '创建线索失败：' + error.message };
}
```

`console.error` 的日志可以在云开发控制台的「云函数 → 日志」里看到，这是云开发唯一的服务端调试手段。

## 2.4 云函数侧的初始化

每个云函数的第一行都是这两句：

```js
// cloudfunctions/authLogin/index.js:1-4
const cloud = require("wx-server-sdk");

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV });
const db = cloud.database();
```

**`cloud.DYNAMIC_CURRENT_ENV` 是什么意思？**

它是个特殊标记，表示「用当前云函数所在的那个环境」。因为一个云函数可以被部署到多个环境（测试环境、生产环境），硬编码环境 ID 的话，换环境就得改代码重新部署。用这个常量，同一份代码在两个环境都能跑。

`cloud.init` 必须在 `require` 之后、使用数据库之前调用。`db` 变量放在模块顶层只初始化一次，能被该函数的所有调用复用。

## 2.5 cloud.getWXContext：云函数怎么知道是谁

这是云开发最关键的一个 API。前端**不需要**传 `openid`，也不应该传——传了就能被伪造。

```js
// cloudfunctions/authLogin/index.js:19-21
const wxContext = cloud.getWXContext();
const openid = wxContext.OPENID;
if (!openid) return { success: false, message: "无法获取 openid" };
```

返回值：

| 字段 | 含义 |
| --- | --- |
| `OPENID` | 当前调用者的微信用户标识，**同一个小程序内唯一且不可伪造** |
| `APPID` | 小程序的 AppID |
| `UNIONID` | 同一微信开放平台账号下的统一标识（本项目没用，未绑定开放平台时为空） |

**为什么 `OPENID` 可信？** 它由微信客户端与微信服务器之间的会话产生，云函数拿到的这份是微信服务端注入的，前端无法篡改。所以整条鉴权链路的起点就是它：

```
用户打开小程序
  → 微信客户端持有登录态
  → 前端 wx.cloud.callFunction
  → 微信服务端验证登录态，注入 OPENID
  → 云函数 cloud.getWXContext().OPENID
  → 拿 openid 查 users 表得到 role / groupId
  → 按 role 决定这次调用能做什么
```

第 11 章会把这条链路完整走一遍。这里先记住一句话：**任何权限判断，起点必须是 `getWXContext().OPENID`，不能是前端传来的任何东西。**

## 2.6 云函数怎么部署

云函数不是保存文件就生效的，必须部署：

1. 开发者工具左侧资源管理器，找到 `cloudfunctions/` 目录；
2. 右键某个云函数 → **上传并部署：云端安装依赖**（推荐）或「所有文件」；
3. 首次使用还要在 `cloudfunctions/` 目录右键 → 「当前环境」选对云环境。

几个实际会卡住的地方：

**依赖要单独装。** 每个云函数目录有自己的 `package.json`，里面通常只有一行 `wx-server-sdk`。用「云端安装依赖」时是云端跑 `npm install`，本地不需要 `node_modules`。

**改了代码必须重新上传。** 这是最常见的「我明明改了怎么没生效」——本地文件改了，云端还是旧版本。

**超时时间默认 3 秒（可调到 60 秒）。** 本项目的 `leadCreateBatch` 要串行写入最多 100 条线索，作者在文档里提醒「100 条在云函数默认超时内通常可行，若环境较慢建议分批 30~50 条」。这是真实约束，不是保守估计。

## 2.7 一个被忽略的能力：前端直连数据库

`wx.cloud.database()` 让前端可以**不经过云函数**直接读写数据库：

```js
// miniprogram/pages/anchor/lead-edit/index.js:31-37
const db = wx.cloud.database();
const res = await db.collection('users')
  .where({ role: 2, groupId: user.groupId })
  .get();
```

这段代码直接查了 `users` 集合，没走云函数。什么时候可以这样？

**可以**：只读、数据不敏感、查询条件简单、结果条数可控。上面这个场景只是拿本团队成员的姓名和 ID 用来勾选。

**不可以**：涉及写操作、涉及跨团队数据、需要按角色决定返回字段。

**为什么？** 因为前端直连受**数据库权限规则**约束，而权限规则只能做到「按记录粒度」控制（比如「仅创建者可读写」），做不到「按角色 + 团队 + 字段」这种复杂逻辑。而云函数以管理员身份访问数据库，**会绕过所有权限规则**——所以复杂的权限判断必须写在云函数里，且要自己写全。

这一点在第 03 章和第 11 章会反复出现，是云开发最容易出安全问题的地方。

## 2.8 练习

1. **观察响应结构**：在 `utils/auth.js:24` 后面加 `console.log(res)`，看完整返回。重点确认 `res.result` 和 `res` 的区别。
2. **加一个云函数**：新建 `cloudfunctions/ping/index.js`，内容 `exports.main = async () => ({ success: true, data: { pong: Date.now() } })`，部署后从任意页面调用并打印。体会「不部署就没反应」。
3. **故意漏掉 .result**：把 `lead-page.js:76` 改成 `if (!res.success)`，跑一次列表页，观察报错。改回来。
4. **验证 openid 不可伪造**：在 `authLogin` 里加 `console.log(wxContext)`，前端调用时在 `data` 里塞一个 `openid: 'fake'`，确认云函数拿到的 `OPENID` 不受影响。
