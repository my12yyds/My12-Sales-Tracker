# 04 查询指令与分页上限

> 本章涉及的 API：`db.command.in/and/or/nin/gte/lt/exists/inc`、`db.RegExp`、`.orderBy()`、`.skip()`、`.limit()`、`.count()`

这一章是本教程最该认真读的一章。原因很直接：**本项目有一处真实缺陷，就是因为忽略了单次查询上限**，而且它藏在一个看起来完全正常的 `.get()` 里。

## 4.1 db.command：等值查询不够用的时候

`where({ groupId: 3 })` 只能表达「等于 3」。要表达「属于 1、2、3 之一」「大于某个时间」「字段不存在」，就要用 `db.command`。

先取个短名字，全项目都这么写：

```js
const db = cloud.database();
const _ = db.command;      // 也有人写成 const _ = db.command，本项目用的是 db.command 全写
```

### 本项目用到的操作符

| 操作符 | 语义 | 本项目位置 |
| --- | --- | --- |
| `in` | 字段值属于数组之一 | `leadCreate/index.js:70`、`:99` |
| `nin` | 字段值不属于数组之一 | `leadList/filters.js:52-53` |
| `and` | 多个条件同时满足 | `leadList/filters.js:85` |
| `or` | 任一条件满足 | `leadList/filters.js:71`、`:81` |
| `gte` / `lt` | 大于等于 / 小于 | `leadList/filters.js:42-48`、`:77-78` |
| `exists` | 字段是否存在 | `leadList/filters.js:81` |
| `inc` | 数值原子自增（写操作用） | 本项目未使用，见[第 03 章](03-云数据库CRUD.md) |

### in：一次查多个 ID

```js
// cloudfunctions/leadCreate/index.js:67-73
const salesRes = await db.collection('users')
  .where({
    _id: db.command.in(assignedSalesIds),   // ['id1', 'id2'] → 匹配其中任意一个
    role: 2,
    groupId: groupId
  })
  .get();
```

这段在做「验证前端传来的成员 ID 是否都合法」。`in` 的好处是一次查询搞定，不用循环 N 次。配合后面的 `salesRes.data.length !== assignedSalesIds.length` 判断，就能发现「有 ID 不属于本团队」的情况。

### gte + lt：时间区间

```js
// cloudfunctions/leadList/filters.js:41-46
if (due === 'today') {
  conditions.push({ nextFollowUpAt: db.command.gte(start) });
  conditions.push({ nextFollowUpAt: db.command.lt(new Date(start.getTime() + DAY_MS)) });
}
```

**注意这里为什么推了两次。** 想表达「今天」= `nextFollowUpAt >= 今天零点` **且** `< 明天零点`。

如果你写成一个对象：

```js
// ❌ 错：后一个覆盖前一个，等于只查了 < 明天零点
{ nextFollowUpAt: db.command.gte(start), nextFollowUpAt: db.command.lt(end) }
```

JavaScript 对象里同名 key 会互相覆盖，最终只剩 `lt`。所以必须拆成两个条件对象，由外层的 `db.command.and([...])` 组合。

这是新手写时间区间最常犯的错，而且**不报错**——查出来的数据就是错的，你得对着结果才能发现。

### and / or：条件组合

`buildFilters` 是整个项目最复杂的一处查询构造，它把一个「筛选表单」翻译成数据库条件：

```js
// cloudfunctions/leadList/filters.js:58-86（节选）
function buildFilters(db, scope, event, options = {}) {
  const conditions = [scope];        // 第一项永远是权限范围
  // ... 逐个 push 可选条件
  if (keyword) {
    conditions.push(db.command.or([
      { phone: db.RegExp({ regexp: literal, options: 'i' }) },
      { customerName: db.RegExp({ regexp: literal, options: 'i' }) },
      { remarks: db.RegExp({ regexp: literal, options: 'i' }) }
    ]));
  }
  // ...
  return { query: conditions.length === 1 ? scope : db.command.and(conditions), order: SORTS[sortKey] };
}
```

三个设计要点：

**第一，`conditions` 数组的第一项是权限范围。** `scope` 是调用方传进来的 `{ groupId }` 或 `{ groupId, assignedSalesIds: userId }`。把它放在最前面，意味着**任何查询都带着权限约束**，后面无论加多少筛选条件都不会绕开它。这是防越权的结构性设计，比在每个分支里手写权限判断可靠得多。

**第二，`and` 只在有多个条件时才包。** `conditions.length === 1 ? scope : db.command.and(conditions)` —— 只有一个条件时直接返回它，避免无意义的嵌套。这属于性能优化，但更重要的是：`db.command.and([x])` 和 `x` 语义等价，少包一层少一次解析。

**第三，`or` 用在「同一字段的多个可能值」上。** 关键词要同时搜电话、名称、备注三个字段，这三个是「或」的关系；而关键词条件和团队范围是「与」的关系。

### exists：字段可能不存在

```js
// cloudfunctions/leadList/filters.js:81
if (event.unfollowed) {
  conditions.push(db.command.or([{ followUpCount: 0 }, { followUpCount: db.command.exists(false) }]));
}
```

「未跟进」的线索有两种形态：`followUpCount` 是 0，或者**这个字段压根没写**（历史数据）。只查 `{ followUpCount: 0 }` 会漏掉后者。

文档型数据库没有 schema，字段缺失是常态。凡是「数值为 0」的判断，都要问一句：**旧数据里这个字段存在吗？**

## 4.2 db.RegExp：模糊检索

```js
// cloudfunctions/leadList/filters.js:70-75
const literal = keyword.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
conditions.push(db.command.or([
  { phone: db.RegExp({ regexp: literal, options: 'i' }) },
  { customerName: db.RegExp({ regexp: literal, options: 'i' }) },
  { remarks: db.RegExp({ regexp: literal, options: 'i' }) }
]));
```

`db.RegExp({ regexp, options })` 和原生 `new RegExp()` 的区别：它是**服务端的**正则，会下推到数据库执行，而不是把数据拉到云函数再用 JS 过滤。

三个必须知道的事：

**第一，必须转义元字符。** `keyword.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')` 把用户输入里的 `.`、`*`、`(` 等全部转义成字面量。不转义的话，用户输入 `.*` 会匹配所有记录，输入 `((( ` 可能让正则编译失败。

顺带一提：正因为做了转义 + 限长 80 字符，这里**不存在 ReDoS 风险**。如果哪天你把这个转义去掉，就得重新评估。

**第二，`options: 'i'` 对中文没有意义。** 中文没有大小写。它对手机号（纯数字）也没意义。真正有用的是英文名、邮箱这类场景。留着不会有明显开销，但别指望它帮你做「拼音搜索」之类的事情。

**第三，正则查询用不上索引。** 只要不是前缀匹配（`^xxx`），数据库只能全表扫描。`remarks` 字段还没有索引，数据量上万后会明显变慢。这是本项目的已知性能边界。

## 4.3 排序与分页

```js
// cloudfunctions/adminDashboard/index.js:27
const res = await query.orderBy('_id', 'asc').skip(skip).limit(PAGE_SIZE).get();
```

| 方法 | 作用 |
| --- | --- |
| `.orderBy(field, 'asc' \| 'desc')` | 排序。可链式调用多个，前面的优先 |
| `.skip(n)` | 跳过前 n 条 |
| `.limit(n)` | 最多返回 n 条 |

排序定义集中在 `leadList/filters.js:1-4`：

```js
const SORTS = {
  newest: ['createdAt', 'desc'], oldest: ['createdAt', 'asc'],
  recent: ['lastFollowUpAt', 'desc'], mostFollowed: ['followUpCount', 'desc']
};
```

用对象做白名单而不是直接接收前端传来的字段名——**这是防注入的必要动作**。如果写成 `.orderBy(event.sort, event.order)`，前端传个不存在的字段名会让查询报错，传恶意值则可能触及其他字段。

## 4.4 单次查询上限：本章的重点

这是云开发最容易埋雷的地方。规则：

| 场景 | 单次 `get()` 返回上限 |
| --- | --- |
| 小程序端（前端直连） | 20 条 |
| 云函数端，**不传 `limit()`** | 100 条 |
| 云函数端，传了 `limit(n)` | 最多 1000 条 |

**注意第二行和第三行的区别。** 很多人以为「云函数里 `get()` 默认能拿 1000 条」，实际上是 100 条；只有显式写 `limit(1000)` 才拿得到 1000。

### 正确写法：分页拉全量

需要「全部数据」时，必须循环分页。本项目有两处正确实现，写法一致：

```js
// cloudfunctions/leadCreateBatch/index.js:10-26
const PAGE_SIZE = 1000; // 云函数单次查询上限
const MAX_SCAN = 20000; // 负载统计与查重的扫描上限，超出时提示改用单条录入

async function fetchAll(collection, where, field) {
  const rows = [];
  for (let skip = 0; skip < MAX_SCAN; skip += PAGE_SIZE) {
    let query = db.collection(collection).where(where);
    if (field) query = query.field(field);
    const res = await query.orderBy('_id', 'asc').skip(skip).limit(PAGE_SIZE).get();
    rows.push(...res.data);
    if (res.data.length < PAGE_SIZE) break;   // 不满一页 = 到底了
  }
  return rows;
}
```

这段代码有四个值得学的细节：

1. **显式 `limit(PAGE_SIZE)`**——不写就拿不到 1000 条；
2. **`orderBy('_id', 'asc')` 必须加**——分页查询如果不排序，数据库返回顺序不保证稳定，可能出现「第 2 页和第 1 页有重复」；
3. **`res.data.length < PAGE_SIZE` 作为结束条件**——比「查到空数组才停」少发一次请求；
4. **`MAX_SCAN` 兜底**——防止数据量异常时无限循环把云函数跑到超时。

`adminDashboard/index.js:20-33` 的 `fetchAll` 是同一个模式，多返回了一个 `partial` 标记，用来告诉前端「数据超过 2 万条了，指标是近似值」。

### 错误写法：裸 get()

同一个项目里，`leadCreate` 的自动分配逻辑漏了这件事：

```js
// cloudfunctions/leadCreate/index.js:96-101
const leadsRes = await db.collection('leads')
  .where({
    groupId: groupId,
    assignedSalesIds: db.command.in(salesIds)
  })
  .get();     // ← 没有 limit，云函数端最多 100 条
```

这段代码在统计「每个成员手上有多少线索」，用来把新线索分给最闲的人。团队线索超过 100 条后，统计只覆盖前 100 条，分配就会持续压给同一个人。

**症状有多隐蔽？** 不报错、不提示、功能看起来正常。只有当你发现「所有新线索都给了同一个人」时才会怀疑到这里。

这个缺陷已被记录为 issue（#25），修复方式是复用 `fetchAll`。留在教程里作为反面教材——**写 `.get()` 的时候，永远问自己一句：这条查询最多可能返回多少条？**

### 顺带一个陷阱：skip 分页的性能

`skip(10000)` 不是「瞬间跳到第 10001 条」，数据库要先**数过前 10000 条**再丢掉。所以 `skip` 分页的复杂度是 O(n²)——翻到后面越来越慢。

大数据量下的替代方案是**游标分页**：

```js
// 用上一页最后一条的 _id 作为下一页起点
db.collection('leads')
  .where({ _id: db.command.gt(lastId), groupId: 3 })
  .orderBy('_id', 'asc')
  .limit(100)
  .get();
```

这样每次都是索引定位，复杂度 O(n)。本项目目前用的是 `skip`（数据量在 2 万以内可接受），这是一个可以优化的点。

## 4.5 练习

1. **复现「时间区间被覆盖」**：在 `dueConditions` 里把 `today` 分支的两个 `push` 合并成一个对象，跑测试，看哪个用例挂了。改回来。
2. **验证裸 get 的截断**：给 `leadCreate` 写个测试，构造 150 条线索（分给 2 个成员，故意让前 100 条都在成员 A 名下），调用创建，观察新线索被分给了谁。这就是 issue #25 的复现。
3. **改一版游标分页**：把 `fetchAll` 的 `skip` 换成 `_id` 游标，跑 `npm test` 确认行为不变。
4. **算一下上限**：本项目 `MAX_SCAN = 20000`，`PAGE_SIZE = 1000`，最多发几次查询？如果数据有 25000 条，会漏掉多少？
