# 07 本地存储与登录缓存

> 本章涉及的 API：`wx.setStorageSync`、`wx.getStorageSync`、`wx.removeStorageSync`

小程序的本地存储是一组**同步** API。同步意味着会阻塞 JS 线程，也意味着写起来不用 `await`——方便，但用不好会拖慢页面。

本章重点不是这三个 API 的语法（它们很简单），而是**什么该缓存、什么不该缓存、缓存脏了怎么办**。

## 7.1 三个 API 的基本用法

```js
wx.setStorageSync('key', value);        // 写
const value = wx.getStorageSync('key'); // 读，不存在时返回 ''
wx.removeStorageSync('key');            // 删
```

对应的异步版本是 `wx.setStorage` / `wx.getStorage` / `wx.removeStorage`（回调式）。本项目全部用同步版，因为都是小数据量的读写，同步写反而代码更短。

### 存储能力限制

| 项目 | 限制 |
| --- | --- |
| 单个 key 大小 | 1 MB |
| 单个小程序总容量 | 10 MB |
| 存储时长 | 永久，除非用户删除小程序或系统清理 |

超限时 `setStorageSync` **会抛异常**，不会静默失败。所以生产代码里应该包 `try/catch`。

## 7.2 必须 try/catch 的原因

```js
// miniprogram/utils/auth.js:35-39
try {
  wx.setStorageSync("user", user);
} catch (e) {}
```

注意那个**空的 `catch`**。这是故意的：缓存失败不该影响主流程。

用户登录成功了，只是「记住登录态」这一步失败（可能是存储满了、可能是系统限制），这时候把用户挡在门外显然不合理——应该让他正常进入，只是下次打开要重新登录。

同样的思路在 `lead-page.js:107-109`：

```js
savePreferences() {
  if (!this._preferenceKey) return;
  try {
    if (this.data.rememberFilters) wx.setStorageSync(this._preferenceKey, cleanPreferences(this.data));
    else wx.removeStorageSync(this._preferenceKey);
  } catch (_) { wx.showToast({ title: '无法保存筛选偏好', icon: 'none' }); }
}
```

这里稍微不同：**保存偏好失败要告诉用户**，因为这是用户主动勾选的「记住筛选」，静默失败会让人困惑（下次打开发现没记住）。但它仍然不阻断任何操作，只是弹个 toast。

**判断标准**：缓存是「锦上添花」还是「功能本身」？前者静默失败，后者要提示。本项目两者都属于前者，所以最多弹个 toast。

## 7.3 两层登录缓存

本项目的登录态用了**两层**缓存，这是刻意设计的：

```js
// miniprogram/utils/auth.js:8-42（节选）
async function login(options = {}) {
  const forceRefresh = options.forceRefresh === true;
  try {
    const app = getApp();
    // 第一层：内存（globalData），最快，但小程序被回收就没了
    if (app.globalData.user && !forceRefresh) {
      return app.globalData.user;
    }

    // 第二层：本地存储，小程序重启后还在
    if (!forceRefresh) {
      try {
        const cached = wx.getStorageSync("user");
        if (cached && cached.openid) {
          app.globalData.user = cached;
          return cached;
        }
      } catch (e) {}
    }

    // 都没有（或强制刷新）：调云函数
    const res = await wx.cloud.callFunction({ name: "authLogin", data: {} });
    // ...
    const user = res.result.data;
    app.globalData.user = user;
    try {
      wx.setStorageSync("user", user);
    } catch (e) {}
    return user;
  } catch (error) {
    console.error("登录失败:", error);
    return null;
  }
}
```

三层优先级，从快到慢：

```
globalData（内存，0ms）
  ↓ 未命中
wx.getStorageSync（本地磁盘，约 1ms）
  ↓ 未命中
wx.cloud.callFunction('authLogin')（网络 + 云函数冷启动，100~3000ms）
```

**为什么要这么设计？** 因为云函数调用有冷启动成本。如果每次页面加载都调 `authLogin`，用户会明显感觉到卡顿。而用户信息（`role`、`groupId`、`name`）在会话期间基本不变，缓存起来完全够用。

**代价是什么？** 缓存可能过期。管理员改了某个用户的角色或团队，用户本地的缓存还是旧的，需要等下次强制刷新。

## 7.4 forceRefresh：什么时候必须绕过缓存

本项目里有两类调用方式：

```js
// 允许用缓存（大多数场景）
const user = await login();

// 强制从云端拉（列表页每次加载）
const user = await login({ forceRefresh: true });   // utils/lead-page.js:36
```

`lead-page.js` 的 `loadLeads` 每次都 `forceRefresh: true`，这是有意的：

线索列表的查询条件依赖 `user.groupId`。如果管理员刚把这个用户调到别的团队，而前端还用旧 `groupId` 查，就会拿到**错误团队的数据**——或者更糟，被云函数拒绝（因为云函数用的是数据库里的真实 `groupId`，两边不一致）。

所以「涉及权限和数据范围的操作，必须用真实值」。

**这是个值得记住的权衡**：

| 场景 | 用缓存 | 理由 |
| --- | --- | --- |
| 页面展示用户名、角色名 | ✅ | 显示错了不影响正确性 |
| 查列表、提交数据 | ❌ 强制刷新 | 数据范围必须准确 |
| 进入首页判断跳哪个页面 | ✅ | 跳错了用户可以自己退出来 |

## 7.5 筛选偏好：key 的命名与白名单过滤

这是本项目里最值得学的缓存设计。

### key 必须带用户维度

```js
// miniprogram/utils/lead-page.js:43
const key = 'lead-filters:' + (user.userId || user._id) + ':' + (isAnchor ? 'anchor' : 'sales');
```

拼出来的 key 形如 `lead-filters:u_123:anchor`。

**为什么要带 `userId`？** 因为同一个手机可能被多个账号登录（换人用、测试账号）。如果 key 只是 `'lead-filters'`，A 用户设置的筛选条件会被 B 用户读到，看起来像「系统自己乱改筛选」。

**为什么还要带角色？** 同一个用户在负责人页面和成员页面的筛选偏好应该分开记。而且这两个页面共用 `lead-page.js`，不加角色后缀会互相覆盖。

### 读出来必须清洗

```js
// miniprogram/utils/lead-page.js:44-50
if (this._preferenceKey !== key) {
  this._preferenceKey = key;
  let saved;
  try { saved = wx.getStorageSync(key); } catch (_) {}
  this.setData({ ...cleanPreferences(saved), rememberFilters: !!saved, keyword: '', leads: [], page: 0 });
  append = false;
}
```

`cleanPreferences` 是关键：

```js
// miniprogram/utils/lead-tools.js:20-28
function cleanPreferences(value) {
  const data = value && typeof value === 'object' ? value : {};
  const date = text => typeof text === 'string' && /^\d{4}-\d{2}-\d{2}$/.test(text) ? text : '';
  return {
    statusIndex: Number.isInteger(data.statusIndex) && data.statusIndex >= 0 && data.statusIndex < 6 ? data.statusIndex : 0,
    sortIndex: Number.isInteger(data.sortIndex) && data.sortIndex >= 0 && data.sortIndex < SORT_OPTIONS.length ? data.sortIndex : 0,
    dueIndex: Number.isInteger(data.dueIndex) && data.dueIndex >= 0 && data.dueIndex < DUE_OPTIONS.length ? data.dueIndex : 0,
    createdFrom: date(data.createdFrom), createdTo: date(data.createdTo), unfollowed: data.unfollowed === true
  };
}
```

这段代码做了四件事，每件都有必要：

**1. 类型兜底**：`value` 不是对象就当空对象。用户可能手动改过 storage，或者旧版本存的是字符串。

**2. 范围校验**：`statusIndex` 必须在 `0~5`（对应 6 个状态选项）。如果本地存的是 `99`，直接拿去 `this.data.statusOptions[99].value` 会 `TypeError` 把页面搞崩。

**3. 格式校验**：日期必须是 `YYYY-MM-DD`。存了个 `"昨天"` 进去，`new Date("昨天")` 得到 `Invalid Date`，传给云函数就是一个非法参数。

**4. 白名单输出**：返回的对象**只包含这几个字段**。存进去时多出来的字段（比如旧版本留下的 `page`、`leads`）全部丢弃。

**为什么第 4 点最重要？** 因为如果直接 `setData(saved)`，本地存储里可能有 `leads` 字段（几 KB 的列表数据）被塞回 `data`，白白渲染一次；更糟的是如果有 `loading: true`，页面会永远卡在加载状态。

**这就是「本地存储是不可信输入」的含义。** 存储在你自己的磁盘上，但内容是历史版本写的、可能被手动改过、可能格式已经变了。当成用户输入来处理，永远不吃亏。

### 关键词为什么不存

```js
this.setData({ ...cleanPreferences(saved), rememberFilters: !!saved, keyword: '', leads: [], page: 0 });
```

注意 `keyword: ''`——**筛选偏好里不包含关键词**。界面上也写明了：

```html
<!-- miniprogram/templates/lead-list.wxml:23 -->
<view class="row-between"><text>记住筛选偏好（不保存关键词）</text><switch checked="{{unfollowed}}" bindchange="onRememberChange" /></view>
```

理由：关键词可能是客户姓名、手机号这类敏感信息。把它明文存在本地存储里，等于在设备上留了一份数据副本。筛选项（状态、排序、日期范围）不敏感，存了无妨。

**这是一个小而重要的隐私判断**：缓存前问一句「这个字段被看到有没有关系」。

## 7.6 清除缓存的时机

本项目有三处清除：

**退出登录**（`profile/index.js:16` 附近）会清掉 `user` 缓存，然后 `reLaunch` 到登录页。

**取消勾选「记住筛选」** 时：

```js
// miniprogram/utils/lead-page.js:107-108
if (this.data.rememberFilters) wx.setStorageSync(this._preferenceKey, cleanPreferences(this.data));
else wx.removeStorageSync(this._preferenceKey);
```

**切换用户**时不需要显式清——因为 key 带了 `userId`，不同用户天然隔离。

## 7.7 什么时候不该用本地存储

三个反例：

**不要存「需要实时一致」的数据。** 比如线索列表。存了之后管理员改了状态，用户看到的还是旧的，还得处理「什么时候失效」的问题。本项目的做法是**列表永远从云端拉**，只在内存里留着当前页数据。

**不要存敏感凭据。** 小程序的本地存储**不是加密的**，开发者工具里可以直接看，真机上 root/越狱后也能读。`openid` 存着问题不大（它不能单独用来登录，还需要微信会话），但 token、密码这类绝对不行。

**不要用它当消息队列。** 有些人用 storage 做「离线待提交队列」，实现起来很麻烦（要处理顺序、去重、失败重试、并发写冲突），而且 10MB 上限很容易撞。

## 7.8 练习

1. **破坏 cleanPreferences**：把 `statusIndex` 的范围校验去掉，手动往 storage 里写 `{statusIndex: 99}`（开发者工具 → Storage 面板），打开列表页，看报什么错。
2. **观察三层缓存**：在 `auth.js` 的三个返回点各加一句 `console.log`，标记「内存命中」「存储命中」「云端拉取」，然后：①首次打开；②退出再进；③杀掉小程序重开。看三次分别是哪一层。
3. **验证 key 隔离**：用两个账号（角色不同）分别设置不同的筛选条件，切换账号，确认互不影响。
4. **加一个字段**：给筛选偏好加一个「只看已逾期」的开关，需要改 `cleanPreferences` 白名单、`data` 初始值、WXML、以及传给云函数的参数。体会「加一个偏好要改四处」——这就是白名单设计的成本。
