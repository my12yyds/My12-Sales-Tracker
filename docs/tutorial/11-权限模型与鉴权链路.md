# 11 权限模型与鉴权链路

> 本章涉及的 API：`cloud.getWXContext`、`wx.cloud.callFunction`，以及 `wx-server-sdk` 的数据库权限行为

前面几章讲的是「怎么用 API」。这一章讲「怎么不被 API 坑」。

云开发最容易出事的地方不是语法，是**权限**。因为云函数以管理员身份跑，数据库不会帮你拦任何东西——所有校验都得自己写，写漏一处就是一个越权漏洞。

## 11.1 三种角色

```js
// cloudfunctions/authLogin/index.js:10-17
/**
 * 角色枚举：
 * 0 管理员（只读）
 * 1 负责人
 * 2 成员
 *
 * 重要：不再自动创建用户。未注册用户会返回 needRegister=true
 */
```

| role | 名称 | 能做什么 |
| --- | --- | --- |
| 0 | 管理员 | 看全量数据、管理用户、删除任意线索；**不能录入/跟进** |
| 1 | 负责人 | 本团队线索的增删改查、分配成员、批量录入 |
| 2 | 成员 | 只看分配给自己的线索，能加跟进 |

两个设计特点值得注意：

**管理员是只读的。** 这不太常见——很多系统里管理员权限最大。本项目刻意让管理员「能看不能改」，理由是：管理员负责统计和人员管理，不该直接介入业务数据。这样「谁改了这条线索」永远是业务人员，责任清晰。

**注册不能自选管理员。** `userRegister` 只接受 role 1 或 2：

```js
// cloudfunctions/userRegister/index.js:29-31
if (![1, 2].includes(role)) {
  return { success: false, message: "请选择角色（负责人/成员）" };
}
```

管理员只能在云开发控制台手动把某个用户的 `role` 改成 0。这是有意的：**开放管理员注册 = 任何人注册就能看全公司数据**。

## 11.2 完整鉴权链路

一次受保护的调用，从点击到数据返回，要过五道关：

```
① 用户打开小程序，微信客户端持有登录态
        ↓
② 前端 wx.cloud.callFunction({ name: 'leadList', data: {...} })
   —— 注意：data 里没有任何身份信息
        ↓
③ 微信服务端验证登录态，往请求里注入 OPENID
        ↓
④ 云函数 cloud.getWXContext().OPENID 拿到可信身份
        ↓
⑤ 用 openid 查 users 表 → 得到 role / groupId
        ↓
⑥ 按 role + groupId 构造查询条件 → 只返回该看的数据
```

**关键在第 ② 步和第 ③ 步之间**：前端不传身份，身份由微信注入。这意味着前端**无法伪造**自己是谁。

### 云函数里的标准三段式

本项目的 16 个云函数，开头几乎一模一样：

```js
// cloudfunctions/adminDashboard/index.js:83-90
const userRes = await db.collection('users').where({ openid }).limit(1).get();
if (userRes.data.length === 0) {
  return { success: false, message: '用户不存在，请先登录' };
}
if (userRes.data[0].role !== 0) {
  return { success: false, message: '只有管理员可以查看数据看板' };
}
```

```js
// cloudfunctions/leadDelete/index.js:20-31
const userRes = await db.collection('users').where({ openid }).get();
if (userRes.data.length === 0) {
  return { success: false, message: '用户不存在，请先登录' };
}
const user = userRes.data[0];
const { _id: userId, role, groupId } = user;

if (role !== 1 && role !== 0) {
  return { success: false, message: '只有负责人或管理员可以删除线索' };
}
if (role === 1 && (!Number.isSafeInteger(groupId) || groupId < 1)) return { success: false, message: '请先分配有效团队' };
```

三段固定结构：

1. **查用户**（用 `openid`，不是前端传的 ID）；
2. **判存在**（查不到就拒绝，不要往下走）；
3. **判角色**（不满足就拒绝，`message` 写清原因）。

**顺序不能换。** 先判角色再查用户，你根本不知道当前用户是什么角色。

## 11.3 数据隔离的三个维度

光判断角色不够。同样是「成员」，A 成员不能看 B 成员的线索。本项目的隔离靠三个维度叠加：

| 维度 | 含义 | 实现位置 |
| --- | --- | --- |
| `role` | 能做什么操作 | 每个云函数的入口 |
| `groupId` | 能看哪个团队的数据 | 查询条件里 |
| `assignedSalesIds` | 成员能看哪几条 | 查询条件里 |

`leadList` 里三者同时生效：

```js
// cloudfunctions/leadList/index.js:29-31、45-56（节选）
if ((role === 1 || role === 2) && !(Number.isSafeInteger(groupId) && groupId > 0)) {
  return { success: false, message: '请先联系管理员分配团队' };
}
// ...
if (role === 1) {
  // 负责人：本团队所有线索
  query.groupId = groupId;
} else if (role === 2) {
  // 成员：分配给自己（assignedSalesIds包含自己）的线索
  query.assignedSalesIds = userId;
  query.groupId = groupId;
} else if (role === 0) {
  // 管理员：所有线索（可选：按组筛选）
  if (event.groupId) { /* ... */ }
}
```

**注意 `role === 2` 那个分支加了两个条件**：既要在本团队，又要分配给自己。

如果只写 `query.assignedSalesIds = userId`，理论上也够（因为分配关系本身就有团队约束），但如果数据里存在「跨团队分配」的脏数据，就会漏。加 `groupId` 是纵深防御。

### 一个真实的越权案例

`followUpList` 里有一段值得单独看：

```js
// cloudfunctions/followUpList/index.js:45-52（节选）
if (lead.groupId !== groupId) {
  // ...
}
if (lead.groupId !== groupId || !Array.isArray(assignedSalesIds) || !assignedSalesIds.includes(userId)) {
  // ...
}
```

这里校验的是「**这条线索是不是我能看的**」。因为跟进记录是挂在线索下的，如果只按 `leadId` 查跟进记录，任何人都能通过猜 `leadId` 看到别人团队的跟进内容。

**这就是「对象级权限」**（也叫 IDOR，Insecure Direct Object Reference）——**光判断「你是谁」不够，还要判断「你访问的这个对象归不归你」**。

凡是接口接收一个 ID 参数（`leadId`、`userId`），都必须多问一句：这个 ID 对应的资源，当前用户有权限吗？

## 11.4 为什么前端判断不算数

本项目前端也有角色判断：

```js
// miniprogram/pages/lead-detail/index.js:98
canManageAssignment: isAnchor && Number.isSafeInteger(lead.groupId) && lead.groupId >= 1,
```

这个判断控制「协作成员管理入口」显不显示。**它只是 UI 控制，不是安全边界。**

原因很直接：小程序的 JS 代码在用户设备上运行。用户可以用开发者工具改内存、可以反编译改包、可以直接构造 HTTP 请求调云函数。所有前端判断都能绕过。

所以前端判断的唯一价值是**体验**：不该点的按钮不显示，减少误操作。

**真正的防线只有一个位置：云函数。** 因为云函数跑在腾讯的服务器上，用户碰不到。

### 一个检查清单

写云函数时，按这个清单过一遍：

- [ ] 身份是从 `getWXContext().OPENID` 拿的吗？（不是 `event.openid`）
- [ ] 查不到用户时直接返回了吗？
- [ ] 角色判断写全了吗？（`role !== 1` 和 `role !== 0 && role !== 1` 是两回事）
- [ ] 如果接收了 `leadId` / `userId`，校验了这个资源的归属吗？
- [ ] 查询条件里带了 `groupId` 吗？
- [ ] 返回的字段有裁剪吗？（`field()` 只给该给的）

本项目在 `docs/MAINTENANCE.md` 里明确写了「这不是对全部云函数和数据库规则的完整安全审计」，是诚实的边界声明。

## 11.5 云函数绕过数据库权限规则

这一点在第 03 章提过，这里展开说，因为它是云开发安全的核心认知。

云开发控制台可以给集合设权限：

| 规则 | 前端直连的效果 |
| --- | --- |
| 所有用户可读，仅创建者可读写 | 能读全部，只能改自己的 |
| 仅创建者可读写 | 只能读写自己创建的 |
| 仅管理端可读写 | 前端完全不能访问 |
| 所有用户不可读写 | 前端完全禁止 |

**但这些规则对云函数完全无效。** 云函数以管理员身份访问数据库，能读写任何记录。

所以有两种截然不同的写法：

```js
// 前端直连：受权限规则约束
const db = wx.cloud.database();
await db.collection('leads').get();     // 只能拿到规则允许的记录

// 云函数：绕过权限规则，什么都能拿
const db = cloud.database();
await db.collection('leads').get();     // 全部记录，无人拦
```

**推论**：如果所有写操作都放在云函数里（本项目就是这样），那数据库权限规则的作用就只剩「防止前端直连读不该读的数据」。而你如果压根不允许前端直连，规则设成「所有用户不可读写」最安全。

本项目是混合的：`lead-edit` 页面前端直连查了 `users`（[第 02 章](02-云开发接入与调用云函数.md) 2.7），其余全部走云函数。所以 `users` 集合的权限规则必须配置好，否则前端能直接读全表用户信息。

## 11.6 怎么给权限写测试

这是本项目最值得抄的工程实践。

云函数依赖 `wx-server-sdk`，本地跑测试时没有真实 SDK。本项目的做法是用 Node 内置的 `vm` 模块造一个假 SDK：

```js
// tests/permissions.test.js:36-42
const cloud = { init() {}, database: () => db, getWXContext: () => ({ OPENID: 'test-openid' }) };
const localRequire = createRequire(path.join(__dirname, '..', 'cloudfunctions', name, 'index.js'));
const sandbox = { exports: {}, require: id => {
  if (id === 'wx-server-sdk') return cloud;
  return localRequire(id);
}, console };
vm.runInNewContext(fs.readFileSync(path.join(__dirname, '..', 'cloudfunctions', name, 'index.js'), 'utf8'), sandbox);
return { main: sandbox.exports.main, calls };
```

拆开看：

1. **`vm.runInNewContext`** 在一个隔离的全局环境里执行云函数源码；
2. **`require` 被劫持**：请求 `wx-server-sdk` 时返回假对象，其余模块走真实 `require`；
3. **`getWXContext` 返回固定的 `OPENID`**，模拟「当前登录的是测试用户」；
4. **`db` 是手写的 mock**，还能记录每次调用的参数（`calls` 数组）。

于是可以写这样的断言：

```js
// tests/permissions.test.js:46-52
test('sales list requires both current group and assignment', async () => {
  const { main, calls } = load('leadList', { _id: 'sales', role: 2, groupId: 2 });
  assert.equal((await main({})).success, true);
  const query = calls.find(call => call.collection === 'leads').where;
  assert.equal(query.groupId, 2);
  assert.equal(query.assignedSalesIds, 'sales');
});
```

**注意它断言的不是返回值，而是「发给数据库的查询条件」。**

这比断言返回值更强：返回值可能是巧合对了（比如数据库里恰好只有一条数据），但查询条件里带了 `groupId` 就证明**隔离逻辑真的生效了**。

```js
// tests/permissions.test.js:54-61
test('unassigned users cannot list leads or follow-ups or create leads', async () => {
  for (const role of [1, 2]) {
    for (const name of ['leadList', 'followUpList', ...(role === 1 ? ['leadCreate'] : [])]) {
      const { main, calls } = load(name, { _id: 'user', role, groupId: 0 });
      assert.equal((await main({ leadId: 'lead', phone: 'test' })).success, false);
      assert.equal(calls.some(call => call.collection === 'leads' || call.add), false);
    }
  }
});
```

第二个断言更狠：**不只是要返回失败，还要确认「压根没去查数据库」**。

为什么？因为如果代码是「先查全表，再在内存里过滤掉不该看的」，返回值也是失败，但数据已经读出来了——万一某个分支忘了过滤，就直接泄露。要求「失败时不许碰数据库」，从结构上杜绝这种写法。

**这个思路可以直接抄到任何项目**：权限测试断言「查询条件」和「有没有发起查询」，而不只是断言返回结果。

## 11.7 已知的权限缺口

诚实地说，本项目还有这些没解决：

| 问题 | 影响 | 记录位置 |
| --- | --- | --- |
| 管理员可以把自己降级，无「最后一名管理员」保护 | 单人部署可能自锁（需进控制台恢复） | issue #26 |
| 没有操作审计日志 | 谁改了谁的角色无从追溯 | issue #26 |
| 注册时手机号无验证、无唯一性 | 手机号真实性无法保证 | issue #27 |
| 注册时角色由用户自选 | 任何人都能注册成「负责人」（但 `groupId=0` 无法操作） | — |

**最后一条值得解释**：`role` 自选看起来危险，但注册后 `groupId` 恒为 0，而所有业务云函数都要求 `groupId >= 1`。所以新注册的「负责人」在管理员分配团队之前，什么也做不了。这是「默认拒绝」的设计。

## 11.8 练习

1. **制造一个越权**：把 `leadList` 里 `role === 2` 分支的 `query.groupId = groupId` 注释掉，写一个测试断言「成员只能看到本团队线索」，看能不能测出来。
2. **读一遍三段式**：打开 `cloudfunctions/` 下任意 3 个函数，找出它们的「查用户 / 判存在 / 判角色」三行，确认顺序一致。
3. **给 followUpCreate 加对象级校验**：检查它有没有校验「这条线索属于我」，如果没有，补上并写测试。
4. **改测试断言**：把 `sales list requires both current group and assignment` 改成只断言返回值，然后故意把 `groupId` 条件删掉，看测试还能不能发现问题。（答案：测不出来。这就是为什么本项目断言查询条件。）
