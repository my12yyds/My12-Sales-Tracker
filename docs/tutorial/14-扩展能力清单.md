# 14 本项目没用到但值得知道的能力

前 12 章讲的都是这个项目里真实存在的代码（第 13 章把它们压缩成了速查表）。这一章反过来：讲 7 个**本项目没用、但同类项目一定会遇到**的能力。

每个都按「是什么 → 什么时候用 → 最小示例 → 本项目哪里本该用它」来说。最后一节解释为什么现在不用。

## 14.1 云存储：文件不该存在数据库里

### 是什么

云开发自带的对象存储（类似 S3）。文件不经过云函数，前端可以直接上传，拿到一个 `fileID`，存进数据库当普通字段。

```js
// 上传
const res = await wx.cloud.uploadFile({
  cloudPath: `leads/${Date.now()}.jpg`,   // 云端路径，需保证唯一
  filePath: tempFilePath                  // 本地临时路径（chooseMedia 拿到的）
});
// res.fileID = 'cloud://env-id.xxxx/leads/1712345678.jpg'

// 换临时可访问链接（默认有效期 2 小时）
const { fileList } = await wx.cloud.getTempFileURL({ fileList: [fileID] });
const url = fileList[0].tempFileURL;

// 下载
const { tempFilePath } = await wx.cloud.downloadFile({ fileID });

// 删除
await wx.cloud.deleteFile({ fileList: [fileID] });
```

### 什么时候用

- 客户附件（合同、截图、录音）
- 头像、商品图
- 任何超过几十 KB 的二进制内容

### 铁律：不要把 base64 存进数据库

数据库单个文档有大小限制（几十 KB 到 1MB 级别），一张手机照片转 base64 就超了。而且数据库按读写次数和存储计费，塞图片会非常贵。

**正确做法**：文件进云存储，数据库只存 `fileID` 字符串。

### 本项目哪里本该用它

`lead-page.js` 的 CSV 导出（[第 08 章](08-设备能力与文件导出.md)）现在只导出「已加载的 20 条」，因为小程序端拿全量会超时。

如果要做「导出全部」，正确路径是：

1. 云函数里生成 CSV 内容；
2. `cloud.uploadFile()` 传到云存储（云函数侧的 `cloud.uploadFile` 接受 `cloudPath` + `fileContent: Buffer`）；
3. 返回 `fileID`，前端 `getTempFileURL` 拿链接再下载或分享。

这样生成过程在服务端，不受小程序端超时和内存限制。

## 14.2 聚合统计：不要在云函数里把全表拉回来算

### 是什么

数据库的聚合管道，语法接近 MongoDB：

```js
const $ = db.command.aggregate;

const res = await db.collection('leads')
  .aggregate()
  .match({ groupId: 3 })                                    // 相当于 where
  .group({
    _id: '$lastStatus',                                     // 按状态分组
    total: $.sum(1),
    followUpSum: $.sum('$followUpCount')
  })
  .sort({ total: -1 })
  .end();
// res.list = [{ _id: 'NEW', total: 12, followUpSum: 30 }, ...]
```

常用阶段：`match`（过滤）、`group`（分组统计）、`sort`、`limit`、`project`（选字段）、`lookup`（类似 join）。

### 什么时候用

**任何「统计」需求**：分组计数、求和、去重计数、Top N。

### 为什么比现在的方式好

看本项目 `adminDashboard` 的做法（[第 04 章](04-查询指令与分页上限.md) 4.4）：

```js
const leadsResult = await fetchAll('leads');       // 把所有线索拉到内存
const allLeads = leadsResult.rows;
// 然后在 JS 里 forEach 数数
```

问题是：

| | 全量拉取 + 内存计算 | 聚合 |
| --- | --- | --- |
| 网络传输 | 全部文档（可能几十 MB） | 只传聚合结果（几 KB） |
| 内存 | 全部文档驻留 | 几乎为零 |
| 数据量上限 | `MAX_SCAN = 20000`，超了就是近似值 | 无上限 |
| 云函数耗时 | 随数据量线性增长，可能超时 | 数据库内部优化，快得多 |

### 本项目哪里本该用它

`adminDashboard` 的所有统计（状态分布、各团队线索量、成员业绩排行）都能用聚合重写，从而彻底去掉 `MAX_SCAN` 和 `partial` 这个近似值标记。

这是 issue #29 建议的方向，也是这个项目最值得做的一次性能重构。

## 14.3 定时触发器：主动做事，而不是等用户打开

### 是什么

让云函数按 cron 表达式定时执行，不需要用户触发。

在云函数目录下加 `config.json`：

```json
{
  "triggers": [
    {
      "name": "dailyDueReminder",
      "type": "timer",
      "config": "0 0 9 * * * *"
    }
  ]
}
```

微信云开发的 cron 是 **7 段**：`秒 分 时 日 月 星期 年`。上面这个表示「每天 9:00:00」。

### 什么时候用

- 每天推送「今日待跟进」提醒（订阅消息）
- 清理过期数据、孤儿记录
- 生成日报/周报
- 定期同步外部数据

### 本项目哪里本该用它

这个项目有完整的「下次跟进日期」字段和「逾期」判定（`filters.js` 的 `dueConditions`），但**只有用户主动打开小程序才能看到**。

加一个定时触发器就能做到「每天早上 9 点，把今天要跟进的线索推给对应成员」：

```js
// cloudfunctions/dueReminder/index.js
const cloud = require('wx-server-sdk');
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV });
const db = cloud.database();
const _ = db.command;

exports.main = async () => {
  const today = /* 中国时区的今天零点 */;
  const tomorrow = new Date(today.getTime() + 86400000);
  const { data: leads } = await db.collection('leads')
    .where({ nextFollowUpAt: _.gte(today).and(_.lt(tomorrow)) })
    .limit(100).get();
  // 按 assignedSalesIds 分组，逐个发订阅消息
};
```

**注意**：主动推送需要用户事先授权「订阅消息」（`wx.requestSubscribeMessage`），不是想推就推。这是微信的硬约束。

## 14.4 云函数互调：复用逻辑的唯一办法

### 是什么

云函数里可以调另一个云函数：

```js
// 在云函数 A 里调云函数 B
const res = await cloud.callFunction({
  name: 'someOtherFunction',
  data: { foo: 'bar' }
});
```

### 为什么需要

[第 01 章](01-项目结构与生命周期.md) 1.1 提过：`cloudfunctions/` 下每个目录**独立部署，不能互相 `require`**。

所以「多个云函数要共用一段逻辑」只有三条路：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 复制粘贴 | 每个函数里写一遍 | 改一处要改 N 处（本项目目前就是这样） |
| 云函数互调 | A 调 B | 多一次调用开销、多一层超时风险 |
| 公共 npm 包 | 发布私有包，各函数依赖 | 维护成本高，适合大团队 |

### 本项目哪里本该用它

`groupId` 校验在 6 个云函数里各写了一遍：

```js
if (!Number.isSafeInteger(groupId) || groupId < 1) { ... }
```

抽成一个 `authGuard` 云函数在理论上可行，但**这里复制粘贴反而更好**：校验逻辑只有两行、几乎不会变、而且多一次云函数调用会让每个请求都慢 50~100ms。

**判断标准**：逻辑短且稳定 → 复制；逻辑复杂且会演进 → 互调或抽包。本项目的选择是对的。

## 14.5 数据库事务：能保证什么，不能保证什么

### 是什么

```js
const transaction = await db.startTransaction();
try {
  const a = await transaction.collection('accounts').doc('a').get();
  await transaction.collection('accounts').doc('a').update({ data: { balance: a.data.balance - 100 } });
  await transaction.collection('accounts').doc('b').update({ data: { balance: _.inc(100) } });
  await transaction.commit();
} catch (e) {
  await transaction.rollback();
}
```

事务内的操作要么全成功，要么全回滚。

### 什么时候用

- 转账、扣库存这类「两边必须同时改」的场景
- 一条记录的写入依赖另一条的当前值（乐观锁）

### 什么时候不能用

**事务有操作数上限，且长事务会超时。** 所以：

- ✅ 适合：2~10 个文档的原子操作
- ❌ 不适合：级联删除上千条记录

这正是 issue #28 讨论的场景。`leadDelete` 要删一条线索 + 它名下所有跟进记录，跟进记录可能有上万条——**包不进事务**。

正确方向是**软删除**（打 `deletedAt` 标记，查询时过滤）或**异步清理**（立即标记删除，跟进记录交给定时任务分批清），而不是硬塞事务。

### 一个更轻的替代：条件更新

不需要事务的场景，可以用「带条件的 update」实现乐观锁：

```js
const res = await db.collection('leads')
  .where({ _id: leadId, status: 'NEW' })      // 只有还是 NEW 才更新
  .update({ data: { status: 'CONTACTED' } });
if (res.stats.updated === 0) {
  // 别人已经改过了，放弃本次修改
}
```

比事务轻，比「先读再写」安全。

## 14.6 自定义组件：页面复用的正经方案

### 是什么

`Component()` 定义可复用组件，有自己的 `properties`、`data`、`methods` 和生命周期：

```js
// components/lead-tag/index.js
Component({
  properties: {
    status: { type: String, value: 'NEW' },
    text: { type: String, value: '' }
  },
  data: { color: '#999' },
  observers: {
    status(value) { this.setData({ color: value === 'WON' ? '#2ecc71' : '#999' }); }
  },
  methods: {
    onTap() { this.triggerEvent('tagtap', { status: this.data.status }); }
  }
});
```

```html
<!-- 使用前先在页面 json 里注册 -->
<!-- {"usingComponents": {"lead-tag": "/components/lead-tag/index"}} -->
<lead-tag status="{{item.lastStatus}}" text="{{item.lastStatusText}}" bind:tagtap="onTagTap" />
```

### 什么时候用

- 一段 UI 在 3 个以上页面出现，且带交互
- 需要对外暴露属性和事件（像一个黑盒）

### 本项目为什么用 include 而不是组件

[第 09 章](09-WXML数据绑定与事件.md) 9.6 讲过：两个列表页用 `<include>` 复用同一个 WXML 模板，配合 `Page(createLeadPage(isAnchor))` 复用逻辑。

这对本项目是合理的：

| | include + 工厂函数 | 自定义组件 |
| --- | --- | --- |
| 适合 | 整个页面结构相同 | 页面里的一段 UI 相同 |
| 数据来源 | 直接用页面的 `data` | 通过 `properties` 传入 |
| 事件 | 直接用页面的方法 | 要 `triggerEvent` 往外抛 |
| 复杂度 | 低 | 高 |

本项目的两个列表页**整页都一样**，用 include 最省事。如果将来要在详情页、看板页也显示「线索卡片」，那就该抽成组件了。

## 14.7 分包加载：主包体积超了才需要

### 是什么

小程序主包有体积上限（2MB），总包 20MB。超过主包上限就编译不过。分包把部分页面拆到独立包里，按需下载：

```json
{
  "pages": ["pages/login/index", "pages/home/index"],
  "subpackages": [
    {
      "root": "packageAdmin",
      "pages": ["pages/dashboard/index", "pages/users/index"]
    }
  ]
}
```

### 什么时候用

- 主包接近 2MB
- 有明显「少数用户才会进」的模块（比如管理后台）

### 本项目为什么不需要

整个 `miniprogram/` 目录很小——没有图片资源、没有第三方 UI 库、没有 npm 依赖，纯代码 + WXSS。离 2MB 差得远。

**判断方法**：开发者工具 → 详情 → 本地代码，看主包体积。不到 1.5MB 就别折腾分包，因为分包会增加路径复杂度和跨包引用的限制。

## 14.8 WXS：WXML 里的轻量脚本

### 是什么

WXML 里不能写复杂逻辑，`{{}}` 只支持表达式。WXS 是可以在 WXML 里跑的一段脚本，用来做格式化：

```html
<wxs module="fmt">
  function money(v) {
    if (!v) return '0.00';
    return v.toFixed(2);
  }
  module.exports = { money: money };
</wxs>

<text>{{fmt.money(item.amount)}}</text>
```

### 什么时候用

- 展示层格式化（金额、日期、脱敏）
- 需要在 WXML 里做判断但 `{{}}` 表达不了的

### 三个限制

1. **不支持 ES6**：没有箭头函数、`let`/`const`、模板字符串。只能用 `var` 和 `function`。
2. **不能调用 `wx.*`**：它跑在视图层，没有 API 能力。
3. **不能改 `data`**：纯函数式，只能返回结果。

### 本项目为什么不用

本项目把格式化放在了 JS 层：`formatDateOnly()`、`getStatusText()`、`dueMeta()` 这些函数在 `setData` 之前就把数据算好了。

```js
// miniprogram/utils/lead-page.js:78-88
const list = (res.result.data.list || []).map(lead => {
  const due = dueMeta(lead.nextFollowUpAt);
  return {
    ...lead,
    lastFollowUpAt: lead.lastFollowUpAt ? formatDateOnly(lead.lastFollowUpAt) : '',
    dueLevel: due.level, dueText: due.text,
    lastStatusText: getStatusText(lead.lastStatus || lead.status)
  };
});
```

**两种方式的取舍**：

| | JS 层预算（本项目） | WXS |
| --- | --- | --- |
| 数据量 | 一次性算好，`setData` 传输的是结果 | 每次渲染都算，但省了传输 |
| 可测试 | ✅ 纯函数，能写单元测试 | ❌ 只能真机看 |
| 复杂度 | 低 | 要学一套受限语法 |

**本项目选 JS 层的决定性理由**：`getStatusText` 这类映射有测试覆盖（`tests/permissions.test.js` 里断言了 `getStatusText('WON') === '已完成'`）。放 WXS 里就没法测了。

## 14.9 为什么这些都没用

诚实的回答：

1. **没有真实需求驱动**。这个项目是单人/小团队用的客户跟进工具，数据量在几千条级别，`fetchAll` + 内存统计够用。上聚合是为了「万一」而上，属于过度设计。
2. **每个能力都有维护成本**。定时触发器要配 cron、要处理推送授权；分包要拆目录；事务要处理回滚路径。没需求时引入，只会增加理解成本。
3. **教程优先展示「够用且正确」的写法**。先学会 `fetchAll` + `MAX_SCAN` 这种带明确边界的写法，比一上来就用聚合更容易理解「为什么要限制」。

**什么时候该引入**：当 `partial` 变成 `true`（数据超过 2 万条）时上聚合；当用户抱怨「要自己打开才知道今天该跟进谁」时上定时触发器；当主包接近 2MB 时拆分包。

**技术选型的原则不是「用最新的」，而是「在约束出现时用对应的解法」。**

## 14.10 练习

1. **用聚合重写一个统计**：把 `adminDashboard` 里的「各团队线索量」改成 `aggregate().group()` 实现，跑 `npm test` 看哪些用例需要改。（提示：测试里的 mock 不支持聚合，这本身就是个学习点——你的测试替身也要跟着升级。）
2. **加一个定时触发器**：给项目加一个「每天 9 点统计昨日新增线索数」的云函数，写 `config.json`，在控制台看执行日志。
3. **抽一个组件**：把列表里的「状态标签」抽成 `components/lead-tag`，在两个列表页和详情页都用上。体会 `properties` 和 `triggerEvent`。
4. **判断要不要分包**：在开发者工具里看主包体积，如果不到 1MB，写下「不需要分包」的判断依据。
