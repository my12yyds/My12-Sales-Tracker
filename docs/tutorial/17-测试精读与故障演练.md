# 17 测试精读与故障演练

> 前面讲的是「代码怎么写」。这一章讲两件更实用的事：**怎么给这类代码写测试**，以及**出故障时怎么快速定位**。

测试部分会逐行拆开 `tests/permissions.test.js` 里的 `load()`——那 30 行是全项目最巧妙的一段代码，看懂它，你就能给任何云函数写测试。

## 17.1 测试不是「跑一遍」，是「可执行的规格」

这个项目的测试不是「跑一下看有没有报错」，而是**把需求写成断言**。

举个具体的：需求说「成员只能看到分配给自己的线索」。这句话怎么验证？

弱一点的验证是「调用接口，看返回几条」。问题在于：库里恰好只有一条属于他的记录时，这条断言也会通过——**即使代码根本没做过滤**。

强一点的验证是：

```js
// tests/permissions.test.js:46-52
test('sales list requires both current group and assignment', async () => {
  const { main, calls } = load('leadList', { _id: 'sales', role: 2, groupId: 2 });
  assert.equal((await main({})).success, true);
  const query = calls.find(call => call.collection === 'leads').where;
  assert.equal(query.groupId, 2);
  assert.equal(query.assignedSalesIds, 'sales');
});
```

它断言的是**「发给数据库的查询条件里，两个字段都在」**。这跟库里有几条数据无关，只跟代码逻辑有关。

这就是「可执行的规格」——把「必须同时按团队和分配关系过滤」这个设计意图，变成一行会失败的断言。

分布说明了取舍：**权限相关（18 个）和查询条件（8 + 7 个）占了大头**。

这不是巧合——这两类代码出错**不会报错，只会算错或漏数据**，而且往往上线很久才被发现。相反，UI 渲染错了用户立刻会反馈，不需要那么多自动化测试。

**测试资源应该按「出错的代价 × 出错后发现的难度」分配，而不是按代码行数分配。**

## 17.3 两种测试替身

这个项目有 11 个测试文件，但只有**两种**「造环境」的方式：

| 方式 | 用于 | 例子 |
| --- | --- | --- |
| 直接 `require` | 纯函数模块（无顶层副作用） | `filters.js`、`lead-tools.js`、`due.js` |
| `vm` 沙箱 | 云函数、页面逻辑（有顶层副作用） | `cloudfunctions/*/index.js`、`lead-page.js` |

### 什么时候可以「直接 require」

```js
// tests/lead-filters.test.js:3-7
const { buildFilters, day } = require('../cloudfunctions/leadList/filters');
const db = { command: {}, RegExp: value => ({ regex: value }) };
for (const key of ['and', 'or', 'gte', 'lt', 'exists']) db.command[key] = value => ({ [key]: value });
```

`filters.js` 顶部只有 `const SORTS = {...}` 这类常量，`require` 它不会执行任何有副作用的代码。所以直接引入，传个假 `db` 就能测。

### 什么时候必须用 vm

云函数不行：

```js
// cloudfunctions/leadList/index.js:1-7
const cloud = require('wx-server-sdk');
const { buildFilters } = require('./filters');

cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV });   // ← 顶层副作用
const db = cloud.database();                       // ← 顶层副作用
```

`require` 这个文件会**立刻执行 `cloud.init()` 和 `cloud.database()`**。本地没装 `wx-server-sdk` 会直接报「模块找不到」；装了的话，它可能尝试连真实云环境。

所以必须「拦在 require 之前」。

## 17.4 逐行拆 load()：五步造一个假云函数

```js
// tests/permissions.test.js:9-44（节选，加注释）
function load(name, user, lead = {}, options = {}) {
  const calls = [];                                    // ① 窃听器
  const db = { /* 手写的假数据库 */ };                  // ② 假 db
  const cloud = {
    init() {},
    database: () => db,
    getWXContext: () => ({ OPENID: 'test-openid' })    // ③ 假身份
  };
  const localRequire = createRequire(path.join(__dirname, '..', 'cloudfunctions', name, 'index.js'));
  const sandbox = { exports: {}, require: id => {      // ④ 劫持 require
    if (id === 'wx-server-sdk') return cloud;
    return localRequire(id);
  }, console };
  vm.runInNewContext(fs.readFileSync(/* 云函数源码 */, 'utf8'), sandbox);  // ⑤ 隔离执行
  return { main: sandbox.exports.main, calls };
}
```

### ① `calls` 数组：测试的窃听器

假 `db` 的每个方法都会往 `calls` 里推一条记录：

```js
// tests/permissions.test.js:16-19
where(value) { this.filter = value; calls.push({ collection, where: value }); return this; },
skip(value) { calls.push({ skip: value }); return this; },
limit(value) { calls.push({ limit: value }); return this; },
```

于是测试可以事后检查「刚才到底发了什么查询」。这是**行为断言**的基础，也是这一章最核心的技巧。

### ② 假 db：只实现用到的方法

```js
// tests/permissions.test.js:11-34（简化）
collection(collection) {
  const query = {
    where(value) { ... },
    orderBy() { return this; },        // 直接返回 this，不记录
    field() { return this; },
    doc() { this.isDoc = true; return this; },
    async get() {
      if (this.isDoc) return { data: lead };
      if (collection === 'users' && this.filter && this.filter.role === 2 && options.members) return { data: options.members };
      if (collection === 'users') return { data: [user] };
      return { data: [] };
    },
    async count() { return { total: 0 }; },
    async update(value) { Object.assign(lead, value.data); calls.push({ update: value }); return {}; },
    async add(value) { calls.push({ add: value }); return { _id: 'new-lead' }; }
  };
  return query;
}
```

**注意 `orderBy` 和 `field` 是空实现**——`return this` 就够，因为它们不影响被断言的逻辑。

这就是「测试替身只需要实现被测试代码用到的那部分」。**不要试图写一个完整的数据库模拟器**，那会变成维护另一个项目。

### ③ 假身份：`getWXContext` 返回固定 openid

```js
getWXContext: () => ({ OPENID: 'test-openid' })
```

这是整套测试的关键一步。云函数里所有权限判断的起点都是 `OPENID`，把它固定住，「当前登录的是谁」就确定了。

**这也意味着：测试无法覆盖「openid 为空」的情况**——除非再造一个 `load` 变体。这是替身的边界，知道就好。

### ④ 劫持 require

```js
const localRequire = createRequire(path.join(__dirname, '..', 'cloudfunctions', name, 'index.js'));
const sandbox = { exports: {}, require: id => {
  if (id === 'wx-server-sdk') return cloud;
  return localRequire(id);
}, console };
```

两件事：

1. **`createRequire` 让相对路径按「云函数自己的目录」解析**。因为 `leadList/index.js` 里有 `require('./filters')`，如果按测试文件的目录解析，会找不到。
2. **`require` 是个函数**，遇到 `wx-server-sdk` 就返回假的，其他原样转发。

**这是「依赖注入」在测试里的手工版本**——不改源码，从外面换掉依赖。

### ⑤ vm 隔离执行

```js
vm.runInNewContext(fs.readFileSync(file, 'utf8'), sandbox);
```

`runInNewContext` 在一个**全新的全局环境**里执行源码。`sandbox` 就是这个环境的全局对象：

- 源码里的 `exports.main = ...` 写的是 `sandbox.exports.main`；
- 源码里的 `require(...)` 用的是 `sandbox.require`；
- 源码里的 `console` 用的是 `sandbox.console`。

执行完之后，`sandbox.exports.main` 就是那个云函数。

**为什么不直接 `eval`？** 因为 `eval` 在当前作用域执行，会污染测试文件自己的变量（比如源码里也有 `const db`，直接冲突）。`vm` 提供隔离。

## 17.5 页面级测试：换个替身对象

页面逻辑用同样的思路，但假的不是 `wx-server-sdk`，而是 **`wx` 对象**：

```js
// tests/lead-page.test.js:8-23
function pageHarness(callFunction, user = { userId: 'sales', role: 2, groupId: 1 }) {
  const calls = [], storage = new Map();
  const wx = {
    cloud: { callFunction },
    getStorageSync: key => storage.get(key),
    setStorageSync: (key, value) => storage.set(key, value),
    removeStorageSync: key => storage.delete(key),
    redirectTo: () => calls.push('redirect'),
    stopPullDownRefresh: () => calls.push('stop'),
    makePhoneCall: value => calls.push(value),
    setClipboardData: value => calls.push(value),
    showToast() {}
  };
  const file = path.join(__dirname, '../miniprogram/utils/lead-page.js');
  const localRequire = createRequire(file);
  const sandbox = { module: { exports: {} }, wx, require: id => id === './auth' ? { login: async () => user } : localRequire(id) };
  vm.runInNewContext(fs.readFileSync(file, 'utf8'), sandbox);
  const page = sandbox.module.exports(false);
  page.setData = values => Object.assign(page.data, values);   // 假的 setData
  return { page, calls, storage, wx };
}
```

三个值得注意的地方：

**1. `storage` 用 `Map` 模拟本地存储。** 于是可以测「记住筛选偏好」这类跨调用的行为——第一次调用写入，第二次调用读出来。

**2. `page.setData` 被替换成同步的 `Object.assign`。** 真实的 `setData` 是异步的（要跨线程渲染），但测试只关心 `data` 里的值，同步赋值就够。**这是替身和真实行为的差异**，测试里不需要关心渲染。

**3. `require('./auth')` 被换成 `{ login: async () => user }`。** 绕过了整个登录链路（三层缓存、云函数调用），直接给定用户。**测试要隔离被测对象**——测分页逻辑时，不该被登录逻辑的 bug 干扰。

## 17.6 三种断言风格

读这 75 个用例，会发现断言有三种：

### 结构断言：检查生成的查询条件

```js
// tests/lead-filters.test.js:10-14
assert.deepEqual(query.and[0], scope);
assert.equal(query.and[1].or[0].phone.regex.regexp, 'a\\.\\*\\[x\\]');
```

`deepEqual` 比对结构，`equal` 比对单值。这是**纯函数测试的主力**。

### 行为断言：检查「有没有做某件事」

```js
// tests/permissions.test.js:54-60
for (const role of [1, 2]) {
  for (const name of ['leadList', 'followUpList', ...(role === 1 ? ['leadCreate'] : [])]) {
    const { main, calls } = load(name, { _id: 'user', role, groupId: 0 });
    assert.equal((await main({ leadId: 'lead', phone: 'test' })).success, false);
    assert.equal(calls.some(call => call.collection === 'leads' || call.add), false);
  }
}
```

第二行断言的是：**失败时压根没碰数据库**。

为什么这条重要？因为「先查全表，再在内存里过滤掉不该看的」这种写法，返回值也是失败——但数据已经读出来了。万一某个分支忘了过滤，就直接泄露。要求「拒绝时不许发起查询」，从结构上堵死这种写法。

### 副作用断言：检查「数据真的变了没」

```js
// tests/lead-batch-create.test.js:120-125
const denied = await asSales.main({ phones: ['13800000041'] });
assert.equal(denied.success, false);
assert.match(denied.message, /主播/);
assert.equal(asSales.store.leads.length, 0);   // ← 一条都没写进去
```

假 db 里的 `store` 就是数据本身，直接数长度。**这比断言返回值更有说服力**——返回值说「失败了」，但数据可能已经被改了一半。

## 17.7 手把手：写一个新测试

**任务**：给「只看已逾期」这个新筛选项写测试。

假设已经按 [第 16 章](16-源码精读-buildFilters.md) 16.10 的 5 步加了代码：

```js
if (event.overdueOnly !== undefined && typeof event.overdueOnly !== 'boolean') throw new Error('逾期筛选须为布尔值');
if (event.overdueOnly) conditions.push({ nextFollowUpAt: db.command.lt(startOfToday) });
```

### 第一步：想清楚要断言什么

三个层次：

1. **正常路径**：传 `true`，条件里有 `nextFollowUpAt < 今天零点`；
2. **类型校验**：传 `'true'`（字符串），抛错；
3. **默认行为**：不传，条件里没有 `nextFollowUpAt`。

**别只写第 1 条。** 类型校验和默认行为才是「将来改代码时最容易破坏」的部分。

### 第二步：选测试文件

`buildFilters` 的新参数 → 放 `tests/lead-filters.test.js`（它已经在测这个函数）。

### 第三步：照着现有用例的写法

```js
test('overdueOnly filter compares against China midnight', () => {
  const { query } = buildFilters(db, scope, { overdueOnly: true }, { today: '2026-10-22' });
  const condition = query.and.find(item => item.nextFollowUpAt);
  assert.equal(condition.nextFollowUpAt.lt.toISOString(), '2026-10-21T16:00:00.000Z');
});

test('overdueOnly rejects non-boolean input', () => {
  for (const value of ['true', 1, null]) {
    assert.throws(() => buildFilters(db, scope, { overdueOnly: value }), /逾期筛选/);
  }
});

test('overdueOnly is absent by default', () => {
  const { query } = buildFilters(db, scope, {});
  assert.equal(query.and ? query.and.some(item => item.nextFollowUpAt) : false, false);
});
```

### 第四步：验证测试真的能失败

**这一步最多人跳过，但它最重要。**

改一行源码（比如把 `<` 改成 `>`），跑测试，确认新用例变红。如果还是绿的，说明断言写错了——测的不是你以为的东西。

```sh
# 故意改坏
$ node --test tests/lead-filters.test.js
# 确认 overdueOnly 相关用例失败
# 改回来
```

本教程里所有「新增测试」的说明都包含这一步，因为**测试的价值等于它能捕获的 bug 数量，而不是它通过的数量**。

## 17.8 故障演练

下面是 8 个真实症状。先自己想「大概是哪一类问题」，再展开看答案。

建议顺序：**先看症状 → 猜方向 → 去代码里找 → 最后对答案**。

---

**症状 1**：列表页打开后一直显示「正在加载…」，数据其实已经回来了（网络面板/日志能看到）。

<details><summary>答案</summary>

`loading` 没有复位。检查三处：

1. 是否在 `finally` 里 `setData({ loading: false })`；
2. 提前 `return` 的分支（比如「未登录跳登录页」）是否也复位了；
3. `wx.hideLoading()` 是否配对。

对应教程：[第 01 章](01-项目结构与生命周期.md) 1.5、[第 05 章](05-交互反馈API.md) 5.3。
</details>

---

**症状 2**：列表里点卡片的**边缘**能进详情，点卡片**中间的文字**没反应。

<details><summary>答案</summary>

用了 `e.target.dataset` 而不是 `e.currentTarget.dataset`。点文字时 `target` 是那个 `<text>`，它身上没有 `data-id`。

对应教程：[第 09 章](09-WXML数据绑定与事件.md) 9.5。
</details>

---

**症状 3**：管理员按团队筛选，选「团队 5」得到空列表，但数据库里明明有团队 5 的线索。

<details><summary>答案</summary>

`groupId` 是字符串 `"5"`，数据库里是数字 `5`，`where` 匹配不到。查 `leadList` 里管理员分支有没有 `Number.isSafeInteger` 校验——修复前是直接 `query.groupId = event.groupId`，静默返回空。

对应教程：[第 06 章](06-页面路由与参数传递.md) 6.3、[第 12 章](12-踩坑清单与调试.md) 12.4。
</details>

---

**症状 4**：「今日待跟进」里出现了上个月的线索。

<details><summary>答案</summary>

时间区间条件被覆盖了。写成 `{ nextFollowUpAt: gte(a), nextFollowUpAt: lt(b) }` 时，同名 key 只剩 `lt`，等于「所有早于明天的」——把历史逾期全算进来了。

正确写法是两个独立的条件对象，由 `and` 组合。

对应教程：[第 04 章](04-查询指令与分页上限.md) 4.1、[第 12 章](12-踩坑清单与调试.md) 12.5。
</details>

---

**症状 5**：客户只填名称不填电话，第一条能录，第二条开始一直提示「本组已存在相同客户电话」。

<details><summary>答案</summary>

查重条件在电话为空时变成 `where({ phone: '' })`，会命中组内所有「仅名称」记录。修法是电话为空时跳过查重。

对应教程：[第 12 章](12-踩坑清单与调试.md) 12.3，以及 PR #31。
</details>

---

**症状 6**：团队线索变多以后，新录入的线索**总是分给同一个人**。

<details><summary>答案</summary>

自动分配时的负载统计用了裸 `.get()`，云函数端只返回前 100 条。超过 100 条线索后统计失真，那个「看起来最闲」的人一直是同一个。

修法：分页拉全量（`fetchAll`），或用聚合统计。

对应教程：[第 04 章](04-查询指令与分页上限.md) 4.4，以及 issue #25。
</details>

---

**症状 7**：改了云函数代码，重新编译小程序，行为完全没变。

<details><summary>答案</summary>

云函数没重新部署。保存文件 ≠ 部署，要在开发者工具里右键「上传并部署」。

确认方法：在云函数里加一句带版本号的 `console.log`，去云开发控制台的日志里看有没有新版本。

对应教程：[第 02 章](02-云开发接入与调用云函数.md) 2.6、[第 12 章](12-踩坑清单与调试.md) 12.10。
</details>

---

**症状 8**：北京时间早上 7 点打开小程序，「今日待跟进」显示的是昨天的数据。

<details><summary>答案</summary>

云函数跑在 UTC。北京时间 7 点是 UTC 前一天 23 点，用 `new Date().getDate()` 或 `toISOString().slice(0,10)` 都得到「昨天」。

修法：手动 +8 小时再取日期，或显式指定时区。

对应教程：[第 12 章](12-踩坑清单与调试.md) 12.11、[第 16 章](16-源码精读-buildFilters.md) 16.6。
</details>

---

**症状 9**（进阶）：成员 A 能刷出成员 B 的线索。

<details><summary>答案</summary>

这是安全问题，不是显示问题。按顺序查：

1. `leadList` 里 `role === 2` 分支是否**同时**设置了 `assignedSalesIds` 和 `groupId`；
2. `buildFilters` 的 `conditions[0]` 是否还是 `scope`（有没有被后续 `push` 覆盖）；
3. 是否存在「先查全表再内存过滤」的写法（应该要求「拒绝时压根不查」）。

对应教程：[第 11 章](11-权限模型与鉴权链路.md) 11.3、[第 16 章](16-源码精读-buildFilters.md) 16.8。
</details>

## 17.9 练习

1. **读一个你没读过的测试文件**：打开 `tests/followup-validation.test.js`，不看源码，先根据测试猜出 `validation.js` 的接口和规则，再去看源码对不对。这是「测试即文档」的实践。
2. **让测试失败**：把 `leadList` 里 `role === 2` 分支的 `query.groupId = groupId` 注释掉，跑 `npm test`，确认有测试变红。**如果全绿，说明隔离逻辑没有被测试覆盖**——那就是要补测试的地方。
3. **写一个测试替身的变体**：给 `load()` 加一个 `openid` 参数，测「`getWXContext` 返回空 openid 时云函数如何反应」。
4. **补一条副作用断言**：给 `leadDelete` 写测试，构造 3 条跟进记录，断言删除后 `store.followUps.length === 0`。
